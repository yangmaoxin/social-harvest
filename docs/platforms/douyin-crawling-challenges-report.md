# 抖音抓取难点报告

这份报告总结抖音适配器这轮开发为什么费劲、当前方案为什么定为“API 主体 + DOM 辅助”、方案的优缺点，以及已经踩过的坑。它用于后续桌面端开发、交付沟通和新平台开发复盘。

## 1. 当前结论

抖音抓取现在已经达到可用状态，但它不是一个纯接口、零页面依赖的理想模型。

当前推荐方案：

- 作品、评论、回复：以 Web API / network 为主。
- 朋友私信：以 `imapi` API 结果为主体，DOM 负责触发页面交互和方向校准。
- 陌生人私信、纯 API 私信方向字段、纯 API 历史翻页：进入 backlog，不阻塞桌面端主线。

一句话判断：

**现在抖音能力足够进入桌面端和统一任务层开发；继续深挖纯 API 的收益已经低于产品化收益。**

## 2. 为什么抖音比预期费劲

### 2.1 抖音不是稳定后台 API 场景

微信视频号主要面向视频号助手后台，很多数据来自比较明确的后台接口。抖音这里混合了几类不同来源：

- 公开 Web 用户主页接口
- 作品评论接口
- 二级回复接口
- 创作者中心私信页面
- 私信 `imapi` protobuf 接口
- 页面 DOM 交互

这些来源的稳定性、鉴权方式、字段结构都不完全一致。尤其私信不是公开数据，它依赖已登录账号本人在创作者中心里可见的页面状态。

### 2.2 用户标识不是外显抖音号

抖音作品链路的关键标识是 `sec_uid`，不是用户看到的抖音号文本。  
这导致一开始不能简单用“抖音号”作为稳定抓取入口。

当前策略是：

- 稳定入口优先使用 `sec_uid`
- 主页 URL 可以解析出 `sec_uid`
- 普通抖音号文本解析先放后续增强

这个取舍让主流程更稳，但也意味着配置门槛比纯后台平台更高。

### 2.3 评论和回复接口会阶段性拒绝

抖音二级回复独立接口在公开 Web 侧可能临时拒绝请求。  
因此不能把“每条回复接口一定成功”作为主流程假设。

当前策略是：

- 一级评论保持主流程稳定
- 二级回复尽量抓
- 回复接口失败时安全降级
- 错误写入报告和失败样本
- 不让单个作品回复失败拖垮整个账号任务

这比“失败就中断”更适合生产跑批。

### 2.4 私信接口是 protobuf 且没有 schema

私信接口不是 JSON，而是 `application/x-protobuf`。没有字段名，只能看到 field 编号、wire type、长度、嵌套结构。

这带来几个问题：

- 正文不一定直接在顶层字段里
- 时间字段需要从候选字段里归因
- 方向字段不能只靠简单枚举判断
- 同一组字段值可能同时出现在入站和出站消息上
- 字段归因需要靠 DOM 真值样本反复对照

这也是为什么私信开发一度很慢：不是“找不到接口”，而是找到了接口以后，还要证明每个字段到底代表什么。

### 2.5 私信页面状态会影响接口返回

私信 API 很多时候需要页面动作触发，例如：

- 切到 `朋友私信`
- 点击左侧会话
- 当前会话已经选中时，先切别的会话再切回来
- 点击 `加载` 才展开更早历史

也就是说，接口不是独立可随便调用的稳定后端契约。它更像前端运行时的一部分。

### 2.6 OpenCLI 页面上下文会抖动

开发过程中多次遇到：

- `stale page identity`
- `Detached while handling command`
- 命令执行页和手工 Chrome 页状态不完全一致
- 页面重开后 `加载` 按钮不一定复现

这不是业务字段问题，而是浏览器运行时和页面生命周期问题。  
因此后续桌面端要把诊断、重试、报告作为一等能力，而不是假设每次页面都稳定。

## 3. 当前方案

### 3.1 作品、评论、回复

当前采用：

- `skill-videos` 抓作品
- `skill-comments` 抓单作品评论
- `skill-harvest` 聚合作品和评论
- `--work-comments` 做作品级评论增强
- `--with-replies` 做二级回复增强
- 失败样本和报告用于断点续跑

这部分已经和视频号主流程基本对齐。

### 3.2 私信

当前采用：

```text
DOM 点击会话 / 加载
        ↓
触发 imapi 接口
        ↓
解析 protobuf 正文和时间
        ↓
用 DOM 可见消息校准方向
        ↓
输出 private-messages-flat.json
        ↓
写入 scrm_message
```

当前明确：

- 内容来源以 API 为主
- DOM 用于交互和方向校准
- 默认只保留入站单聊
- 默认过滤自己发送和疑似群聊
- `private-messages-report.json` 可供桌面端读取

## 4. 方案优点

### 4.1 已经能支撑业务闭环

当前抖音已经具备：

- 作品入库 `scrm_file`
- 评论和回复入库 `scrm_comment`
- 私信入库 `scrm_message`
- MySQL upsert 和 verification 验证
- 失败样本、报告文件和诊断文件

这已经不是单点 demo，而是可以进入产品化的一条链。

### 4.2 不追求纯 API，稳定性更现实

私信纯 API 目前还差方向字段、历史翻页和陌生人私信闭环。如果继续把这些当主线，会拖慢桌面端。

当前混合方案的好处是：

- API 拿正文和时间，避免纯 DOM 文本解析脆弱
- DOM 负责触发用户真实可见范围，符合本人授权边界
- DOM 真值能校准方向，避免 API 字段误判
- 能先交付，后续再局部增强

### 4.3 和桌面端目标匹配

桌面端本来就要连接用户自己的 Chrome 和登录态。  
所以“DOM 交互触发接口”不是完全不可接受的负担，只要我们做好：

- 诊断
- 禁止重复点击运行按钮
- 重试
- 报告
- 可恢复提示

这比为了纯 API 把项目卡住更划算。

## 5. 方案缺点和边界

### 5.1 私信还不是纯 API

当前私信仍依赖：

- 页面能打开
- 登录态有效
- 会话卡能点击
- `加载` 按钮能被当前页面状态呈现
- DOM 可见消息能用于方向校准

这意味着无人值守稳定性不如纯后端接口。

### 5.2 陌生人私信还没作为正式链路

已经定位到相关接口：

- `v1/stranger/get_messages`
- `v1/stranger/mark_read_conversation`
- `v2/conversation/get_info_list`

但陌生人私信还没有做到和朋友私信一样的字段归因、导出和入库闭环。

### 5.3 历史消息翻页仍依赖页面状态

`加载` 按钮已接入，但它是否出现取决于当前会话页面状态。  
手工 Chrome 页和命令页状态可能不一致，这个问题不能只靠选择器修掉。

### 5.4 方向字段仍有 DOM 校准成分

API 里简单的方向候选值曾经被样本证伪。  
现在已经有 `dom_match` 和 `visible_fingerprint` 辅助，但纯 API 方向字段还没完全收口。

## 6. 这次开发踩过的坑

### 6.1 默认适配器和自维护适配器混用

一开始需要确认到底是不是还在走 OpenCLI 默认 `user-videos`。  
后来已切到自维护 `skill-harvest`，避免 OpenCLI 更新覆盖同名默认逻辑。

经验：

- 关键平台能力要使用自维护命令名和同步脚本
- 文档里必须写清楚主命令实际调用的是哪条链路

### 6.2 私信一层列表和二层会话不是同一个问题

私信第一页能看到会话，不代表二层能稳定读取消息。  
二层左侧列表、右侧消息面板、当前选中态、接口触发时机都是独立问题。

经验：

- 会话列表要有 `thread-list-probe`
- 会话结构要有 `thread-structure-probe`
- DOM/API 对照要有 `dom-api-match-probe`
- 不要只凭截图判断自动化是否真的点中了目标

### 6.3 `thread_rank` 曾经漂移

早期 `thread_rank=8` 可能误落回第 1 条会话。  
后来通过二层左侧列表、卡片去重、越界空返回，把这个问题收住。

经验：

- rank 必须和实际可见会话列表绑定
- 越界应该返回空，不应该回退点其他会话
- 重复 DOM 壳子必须按卡片根节点去重

### 6.4 字段候选不能凭一次样本下结论

一度认为 `2:1,11:0,12:0` 可以代表出站。  
后来真实入站样本也出现了同一组候选值，说明这个判断不成立。

经验：

- 方向字段必须用入站和出站同时验证
- 同一个字段集合不能直接视为方向真值
- 需要保留 `direction_source`，告诉后续使用者方向来自哪里

### 6.5 DOM 过滤误伤真实正文

曾经把裸词 `消息` 当成 UI 噪音过滤掉。  
用户发送“消息很多”“消息多多的确实”后，这类真实正文被误杀。

经验：

- 噪音过滤不要用过宽的单字词
- 与业务正文可能重叠的词要谨慎
- 真实样本比假想样本更容易暴露问题

### 6.6 `加载` 按钮不是每次都能复现

手工 Chrome 页出现 `加载`，点击后能展开历史消息。  
但 OpenCLI 命令页多次看不到同一个按钮。

经验：

- 页面上下文状态可能不一致
- 不要把一次手工页面状态当成命令页事实
- 诊断要输出按钮数量、滚动容器、候选位置和点击次数

### 6.7 page identity 抖动会误导判断

多次出现 `stale page identity` 和 `Detached while handling command`。  
如果没有重试和诊断，很容易误判为字段解析失败。

经验：

- 先复用当前 page，必要时再 reset
- 单个 rank 失败不能拖垮整轮扫描
- 诊断输出要保留错误类型和恢复建议

## 7. 和视频号的差距

数据能力层面，抖音已经基本追上视频号：

| 能力 | 视频号 | 抖音 |
| --- | --- | --- |
| 作品 | 已支持 | 已支持 |
| 图文识别 | 已支持 | 已支持归一化 |
| 评论 | 已支持 | 已支持 |
| 二级回复 | 已支持 | 已支持，失败降级 |
| 私信 | 已支持 | 朋友私信可用 |
| SCRM 入库 | 已支持 | 已支持 |
| 报告文件 | 较完整 | 私信已有，主流程需继续统一 |

工程产品化层面，抖音还需要继续补：

- 统一任务事件
- 更完整的 `run-report.json`
- 失败恢复建议
- 桌面端可直接消费的状态模型
- 更系统的长期运行稳定性验证

## 8. 当前计划

当前不再把“纯 API 私信”作为主线。

优先级如下：

1. 冻结抖音私信当前方案：API 主体 + DOM 辅助。
2. 做统一 runner：让桌面端和 CLI 复用同一任务入口。
3. 做统一事件和报告：让 UI 读取任务状态，不解析零散 stdout。
4. 把抖音公开主页 / 创作者中心两条流程的报告补齐到接近视频号。
5. 桌面端接入任务创建、运行、日志、报告、入库结果。
6. 把陌生人私信、纯 API 方向字段、纯 API 历史翻页放入 backlog。

## 9. 对后续开发的建议

- 不要再以“是否纯 API”判断当前抖音私信是否可用。
- 每次改私信方向逻辑，都必须带入站和出站样本验证。
- 每次改 DOM 选择器，都要用 `dom-detail-probe` 和 `thread-list-probe` 验证。
- 桌面端诊断按钮要做到运行中禁用，避免重复点击造成假失败。
- 抖音页面相关失败要优先归类为登录态、页面状态、OpenCLI page identity、字段解析四类。
- 新平台开发时，优先复用这套报告思路：先定义可交付边界，再做深层接口研究。
